The architecture separates facts, simulation, calculation, and narrative. That separation makes results testable and keeps an AI failure from taking the whole system down.

The browser calls the frontend, the frontend forwards to the API through a server-side proxy, and the API persists state to PostgreSQL while pushing heavy work to the worker through Redis. The worker is the only component that talks to the evidence provider, OCR, and the LLM provider.

## Component responsibilities

| Component | Responsibility | What it does not do |
|---|---|---|
| Next.js frontend | Input, route guards, job status, rendering results | Compute scores, money, or aggregates |
| FastAPI | Authentication, validation, authorisation, use-case API | Run simulation or OCR on the request thread |
| Celery worker | Analysis, OASIS, OCR, PDF, recovery, retention | Act as the source of truth for state |
| Celery beat | Schedule run reconciliation and artifact retention | Alter run results |
| PostgreSQL | System of record for identity, businesses, transactions, evidence, analyses, events, artifact metadata | |
| Redis | Celery broker and event transport | Store the final report |
| Object storage | Private receipt photos and PDFs behind signed URLs | Hold permanently public objects |
| OCR | Turn a receipt image into a draft with confidence | Create a final transaction |
| LLM provider | Run agents through the CAMEL adapter | Produce authoritative numbers |

The frontend calls the backend through a server-side proxy route, so the browser uses same-origin API paths and provider credentials never reach the client bundle.

## Market Analysis flow

1. The API validates input, education prerequisites, and the idempotency key.
2. The API stores a `queued` run with an immutable input snapshot, commits, and dispatches the task.
3. The worker collects the evidence snapshot. Every field carries a source, observation time, and quality.
4. The orchestrator builds structured context and runs the four councils.
5. The deterministic engine computes finance from typed input, then scoring applies versioned rules.
6. The report council composes the narrative only from validated artifacts.
7. Validators check schema, citations, and arithmetic consistency.
8. The run becomes `completed`, `partial`, `failed`, or `cancelled`.

State is persisted to PostgreSQL before an event is published through Redis. That ordering is what makes the polled snapshot a legitimate reference whenever SSE drops.

The stage order is linear. The `building_context -> calculating_finance` branch applies when a deployment has no agent adapter at all, so the `simulating` stage leaves the plan and is reported as skipped rather than credited as completed work. The first three terminal states are decided at `validating_report`; `cancelled` completes the state machine for a run stopped before it finishes, and the diagram shows two example exit points.

Each run stores the input snapshot, evidence snapshot, correlation ID, idempotency information, model manifest, prompt manifest, cohort, seed, budget, and agent artifacts.

## Receipt photo flow

```text
created -> uploading -> queued -> preprocessing -> extracting
  -> ready_for_review -> confirmed -> committed
  | failed | cancelled
```

The upload goes straight from the browser to object storage through a signed URL, so large files never pass through the API. OCR runs on a separate worker queue so a large image cannot hold up ordinary transaction requests.

## Storage responsibilities

- **PostgreSQL** is the system of record. Money is stored as integer rupiah, time in UTC, and identifiers are UUIDs with no business meaning.
- **Redis** holds queues and short-lived event transport. Lost jobs are reconciled from PostgreSQL state, not from Redis.
- **Object storage** holds receipt photos and export PDFs as private objects.
- **OASIS traces** are written per run into a unique directory, registered as an artifact, and removed by an explicit retention job. No global trace file is overwritten between runs.

## Resilience patterns

- Idempotency keys prevent duplicate analyses, transactions, and exports.
- A recovery lease keeps a live task from being reclaimed too early while still allowing a run whose worker died to return to the queue.
- Separate timeouts per data provider and per LLM call.
- Retries only for transient errors. Schema or policy errors are not repeated unchanged.
- Hard per-run budgets for persona count, rounds, concurrency, tokens, and wall clock.
- A deterministic fallback when OASIS fails, producing a `partial` result.
- SSE can resume with `Last-Event-ID`; snapshot polling is the backup.
- A correlation ID flows from the API through Celery, the OASIS trace, the report, and the logs.

## Repository boundaries

Frontend, backend, and documentation are three separate repositories with no cross-directory imports. The contract between them is the HTTP API and the OpenAPI schema, not a shared module. Code structure details are in [Code structure and standards](/en/docs/engineering/struktur-dan-standar).
